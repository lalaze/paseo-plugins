## 2026-10-14：未领取恢复机制

新增两分钟未领取提示、2/4/8 分钟间隔的最多三次自动补发，以及详情顶部的「重新唤醒 Dot」按钮。恢复计数持久化到轮次，重启不重置；手动补发保留轮次和消息，按操作 ID 去重并限制每分钟一次。已领取、已停止或已完成的轮次不自动补发，也不因超时冒充停止或释放名额。

- 处理于 09:03:42 启动，09:04:23 前失败；精确工具开始时间未保留，脚本显示 wall time 8.4 秒。
- 失败工具是 `list_dot_tasks`，只带 connectionId，并未执行 `get_dot_task`、`claim_dot_task` 或结果提交。
- 可见错误为 `SyntaxError: Unexpected token 'u', "user cance"... is not valid JSON`，调用位置 `JSON.parse` / `exec_main.mjs:1:134`。
- Dot 未保留导致解析异常的完整原始返回，因此取消来源、是否权限拒绝仍未知。不能把它断言为 Bridge 业务错误，也不能把“user cance”直接等同于用户在本会话主动取消。

这次长时间不动的具体机制是：收到事件 → 列举任务工具/包装层返回非 JSON 内容 → Dot 生成的处理脚本盲目 JSON.parse 后退出 → 尚未领取，Bridge 持续显示等待。前述缺少未领取恢复机制会放大该失败。

已在原始 Dot 持久规则中将已知 taskId 的事件改为直接 `get_dot_task`，仅缺少 taskId 时才列表；新增工具结果类型与错误检查、受保护的 JSON 解析、保留真实错误、只对明确瞬时只读网络错误有限重试、尊重明确取消与权限拒绝、未领取失败在 Dot 主页报告的要求。原权限和其他交付指令保留。保存后重新打开核验：直接读取、错误检查、持久约定均存在，旧的 list-first 指令不存在。此修改是模型执行规则的修正，不是对平台取消机制或 Bridge 源码的修复。

## 结论与证据边界

### 补充：进一步核查实际接收入口

通过用户现有 Chrome 标签页只读核对，发现此前笼统使用“Dot”描述所有成功领取者并不准确：

- 普通 Work 聊天「恢复自动处理」的可见历史明确记录：原始规则管理不可见后，另建「Paseo 原生文字自动回复」，并将本机任务通知路由切换过去。该替代规则现在显示 Paused。
- 另一个普通 Work 聊天「创建自动回复规则」创建了「Paseo Dot 文字回复」（规则 ID `6acc94ef416881918e222ac169f4fbd0`）。该规则当前 Monitoring，指令要求文字任务读取、领取、回传，以及工具失败后安静结束；高级设置显示 Same chat for every run。它是普通聊天中的替代处理规则，不能仅凭名称认为由 Your dot 本体执行。
- 本机 v7 备份的原始 `task_changed` 订阅 ID 是 `bb4ff1f9c2712fd8bc6c3bb413e6b03f`；当前已不存在。当前唯一任务事件订阅是 `98cfc00437759724034059f2b89eafe2`，创建于纽约时间 04:06:04.982，回调地址也已变化，与新普通聊天规则的创建阶段吻合。原始 `connection_test` 订阅 `f379a51aaaa71c916d091c3024ae14c4` 及其回调地址仍保留。

因此，本机当前并没有继续向原始 Dot 的任务回调投递。连接测试成功仍不能验证任务通知接收方正确。新规则与当前新回调的关联有创建时间和可见创建历史支持，但管理界面没有提供可直接读取的规则 ID → 回调 ID 映射；不把时间关联写成后台映射查询结果。

[官方 MCP Events 文档](https://developers.openai.com/plugins/build/mcp-events) 说明事件在订阅它的聊天中处理，2xx 只确认接收、之后异步执行，而且可能按任务的 batching 设置合并事件。本次界面把额外触发设置显示为 Additional settings are not shown，无法据此确定实际 batching 参数或其延迟。

原普通聊天的可见恢复历史还明确指出：03:12 的问候由直接提示后手动领取并回传。故该例的“创建到领取 15 分 57 秒”不是可用于衡量自动唤醒性能的样本。其余领取的具体执行者和触发时间也没有完整只读运行记录，不能把所有成功回传当作原始 Dot 自动执行的证据。

本次没有新建、暂停、修改或切换任何规则，也没有发送聊天消息或重放业务事件。下一步恢复用户希望的 Your dot 路径时，应由原始 Dot 规则重新建立真实任务订阅并验证收到事件；不能拿普通聊天的自动规则代替，也不应猜测/手工拼造回调地址。此前复现的本地可靠性缺陷仍成立，但与上述接收入口变化是不同的问题。

实际卡点在事件回调送达之后、当前轮次成功 `claim_dot_task` 之前。Bridge 没有对“已送达但一直未领取”做超时检测或补偿唤醒，因而一次未执行的通知就能变成无限等待，并占用并发名额。

另外复现了通知早于派发、派发通知被去重吞掉的竞态，以及订阅更新唤醒终态旧任务的问题。竞态是确定的代码缺陷，但没有足够的线上领取失败日志，不能认定它就是每次实机停顿的触发原因。Dot 端为什么没有成功领取（未执行、延迟执行、调用失败等），本机现有记录无法进一步区分。

本次只做诊断，新增本说明和隔离复现脚本；未修改生产代码、运行状态、订阅或用户会话。

## 已复现的三个问题

### 1. 回调成功之后没有领取确认超时处理

- `server/engine.ts:1245`：`delivered` 的事件以后直接跳过。
- `server/engine.ts:1363`：HTTP 2xx 即判定回调送达，不代表 Dot 已执行任务。
- `server/engine.ts:856`：调度只派发 `queued`；没有检查长期未领取的 `dispatched`。
- `shared/schema.ts:386`：`dispatched` 已占用并发名额。
- `server/provider.ts:56`：上述状态持续让本地会话等待。

隔离复现：回调返回 200，但不领取。模拟 60 分钟的调度和投递并调用恢复流程，第一项始终 `dispatched`，补发次数为 0；并发上限为 1 时第二项始终 `queued`。这解释了为何传输通了仍会卡死，以及多个未领取任务如何阻塞后续会话。

### 2. 连续追问存在“先通知、后可领取”的丢唤醒竞态

- `server/engine.ts:606`：`providerPrompt` 为追问新建 `queued` 轮次，同时发出 `message_added`。
- `shared/machine.ts:158`：尚为 `queued` 的轮次不能领取。
- `server/engine.ts:901`：派发后调用 `wake`。
- `server/engine.ts:1454`：同任务只要已有未完成投递的事件，就不生成新唤醒；没有区分该事件是在派发前还是派发后被读取。
- `index.server.ts:124`：一次 tick 内先调度再投递，但 prompt 可插入两者之间，多个异步 tick 也可交错；没有跨整个 tick 的串行保证。

复现顺序：先完成第一轮 → 一个 tick 检查队列 → 用户追问入队 → 该 tick 投递追问 → 回调侧尝试领取，得到 `claim-rejected / queued` → 下一 tick 在回调尚未结束时派发 → `wake` 看到旧事件 pending，不再发通知 → 回调返回 200 → 最终任务 `dispatched`、未领取、没有剩余唤醒。

脚本通过受控 Promise 精确复现该顺序，不依赖随机 sleep。正常顺序下现有多轮 provider 测试仍通过，因此先前多轮成功验收不能排除此竞态。

### 3. 订阅更新会重发终态旧任务

`server/engine.ts:423` 对所有任务调用 `wake`，未筛选模式、状态或是否仍有待处理输入，也未限定必须是任务事件订阅更新。

隔离复现：一个已完成任务、一个已停止任务，在刷新订阅后各获得一条新的 `created` 事件。

实机 04:06:05.971 附近同时生成了 15 条任务通知，其中 13 项在当时已经完成或请求停止，包含历史 Git 任务。这是确定存在的无效唤醒；它是否造成 Dot 侧排队或延迟，尚无远端执行记录证明。

## 修复方向

1. 将排队中的消息持久化与“可领取”唤醒区分开。派发成功必须有属于当前轮次、当前输入且反映可领取状态的通知，不能被派发前已经开始处理的事件抑制。
2. 为当前轮次增加领取确认期限和有限、退避的补偿唤醒；以领取为完成确认。已领取、完成、停止或过期轮次应停止补偿，避免重复执行。持续无确认时向用户明确显示“已送达但未领取”，而不是永久转圈。
3. 订阅恢复仅唤醒该连接下仍需处理的有效任务，排除已结束和不可执行的历史记录。
4. 持久记录事件发送/响应时间、领取尝试与拒绝原因（不记录令牌和消息正文）。这才能区分 Dot 未执行和实际领取被拒，并验证修复后连续多轮是否可靠。

以上能修复本地确定的问题；Dot 端是否始终按通知执行，还需要在修复后以真实订阅做连续多轮验收，不能以 HTTP 200 或一次文字回传代替。
