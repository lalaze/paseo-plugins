# paseo-todo 设计

独立插件 `todo/`，id `paseo-todo`。侧栏「待办任务」只负责创建和验收。执行在插件服务进程里，关掉前端不会停队列。不读取、不迁移、不复用已归档的 `director/` 数据或调度器。

## 状态

`draft` 草稿 → `queued` 排队 → `preparing` 准备（已写入 operation id）→ `running` 执行中。

权限请求只把 `running` 改成 `needs_attention`（待权限）。`permission_resolved` 回到 `running`。这两种都不是完成。

没有开启协作的任务，只有 `agent.turn_ended` 的 `outcome.kind` 能结束一轮：

- `completed` → 在任务分支上固化提交后进入 `awaiting_review`（待验收）
- `failed` → `failed`
- `canceled` → `canceled`

权限按请求 id 记账：同一会话还有未处理的请求时，处理掉其中一个不会回到 `running`。

没有 `idle` 这条路径。服务重启后，`canceling` 的任务重新发出取消并按取消收尾，不会因为会话仍在跑而退回 `running`。其余执行中的任务若没有已保存的 outcome，且会话已不在跑、也没有待处理权限，进入 `needs_check`（待核对），不重新发送。会话仍在跑则只继续等待下一次 `turn_ended`。

开启协作的任务不把主 Agent 某一次 `turn_ended` 当成整次协作结束。设计、执行、审核、最终审核和等待方案确认都保持执行占用。宿主进入等待会话验收后才固化成果并进入待办待验收；此时会话验收是 pending，合并会被拒绝。宿主阶段变为 completed 后记为会话已验收，待办合并仍要用户按页面上的成果绑定显式确认。方案批准和会话验收都在会话里完成，插件不伪造消息，也不代用户批准或验收。

`canceling` 期间忽略成功结果，最终记为 `canceled`。`merging` 与取消互斥：合并锁持有时取消直接拒绝。

同一仓库一次只执行一个任务。队列锁、Git 写锁与合并互斥均以真实 `git common-dir` 标识仓库，同一仓库的多个 worktree 共用锁；任务仍保存各自的工作目录。创建任务及重启恢复时解析身份，旧存档不需要迁移。排队任务派发前若仓库身份解析失败，保存为 `failed` / `prepare-failed` 并显示错误，路径恢复后可重试；错误不能覆盖期间发生的取消或新一轮排队。关闭插件时等待进行中的解析与失败写盘完成。准备工作树、固化成果和合并这几步 git 写操作另有一把短锁串行，合并不必等同仓库另一个任务的整轮执行结束。锁的顺序固定为先任务锁、后 git 锁。待验收不占用执行名额。不同仓库可以并行。

需要新会话的继续修改或重试，先停止并检查上一轮会话；检查失败、仍在运行或等待权限时拒绝创建新会话。这也适用于单 Agent 在待验收后被用户重新启动的轮次。确认停止后分配新的 operation id、清掉旧的验收绑定，并新建一个 Agent。继续修改时新会话收到的是原任务内容加上打回意见，工作树沿用上一轮。旧会话上的 `turn_ended` 不能推进新一轮。事件缓存按 agent 与 turn 记录，处理过后即删除；重复回调和已经对不上当前 `turn_started` 的回调不再固化成果。排队且还没有 operation id 的任务才允许派发。

`agent.turn_started` 落在已有验收绑定的会话上不再直接作废绑定；该轮 `turn_ended` 时按绑定快照核对工作树：成果 commit 与 tree、目标 HEAD、工作树干净程度全部一致（例如只是向会话提问）则绑定保留、仍可验收，对不上或核对失败才改为待核对并清掉绑定。验收前再检查该会话：仍在执行、仍有待处理权限，或检查本身失败，都不进入合并，也不改已保存的绑定。

取消在创建会话之前和之后都要收尾。只有确认没有会话，或检查明确显示会话已停止且没有待处理权限，才写成已取消并放开该仓库。检查失败保持 `canceling`，仓库继续被占用。插件关闭时先停止新的派发，等已经开始的准备、固化、合并和写盘结束后才释放数据目录锁；关闭之后的回调不再写盘。

## 删除任务

通过 `deleteTask`（RPC `delete-task`，入参 `{ id }`）删除任务。非执行状态（`draft`、`queued`、`awaiting_review`、`needs_check`、`failed`、`canceled`、`merged`、`merge_failed`）允许删除；执行中或合并中的任务（`preparing`、`running`、`needs_attention`、`canceling`、`merging`）拒绝直接删除（返回 `delete-rejected`，需先取消或等待完成）。删除时先停止并确认关联协作 run 与 Agent 已停止，再依次归档会话工作区、移除工作树、删除任务分支；已合并且绑定仍在的分支走 `deleteMergedBranch` 的安全校验，其余强制删除。任一步失败立即停止，保存 `delete-failed` 和错误详情并保留任务记录，用户处理错误后可再次删除。已合并任务复用 `cleanup` 中成功的步骤；全部清理完成后只删除存档，不再依赖旧会话或仓库可访问。仅在所有步骤成功后从 `state.json` 永久移除。前端在卡片及详情抽屉提供带二次确认的删除操作。

## 验收绑定

进入待验收时记下：成果 commit、成果 tree、目标分支、当时的目标分支 HEAD、本轮 `turnId`。

「验收并合并」的请求体是 `{ id, review }`。`review` 必须是用户当时在页面上看到的那份绑定，服务端与当前存档逐项严格相等，否则返回 `stale-client-review`，不进入合并，也不改写已保存的新绑定。这样旧页面不能只凭任务 id 批准后来的新版本。Git 与存档是否仍一致是通过这道比较之后的另一次检查。

固化成果和投递合并指令前都确认任务目录的 git common-dir 属于该仓库，且当前分支就是任务分支。对不上就停止，不对错误分支 `git add` 或 `commit`。任务工作树若已有 merge、rebase、cherry-pick、revert，直接拒绝。合并指令要求 Agent 遇到脏目标工作树或已有 Git 操作时停止；合并后的验证也检查目标工作树。

`state.lock` 是一个独占创建的目录，目录存在即表示锁被持有。空文件、无效内容、尚未写完的 owner 记录或已退出进程的 pid 都不会被删掉来抢锁。只有创建这把锁的进程在 `dispose` 时移除它。拿不到锁的进程不调度。状态变更先串行写入 `state.json`，成功后才发布到内存；写失败时后续调度仍看见上一份已落盘的任务。

以下任一情况都使绑定失效，状态改为待核对，合并函数不会被调用：

- 任务分支 HEAD 或 tree 变化，或工作树变脏（包括用户打开同一会话后又改了文件）
- 目标分支 HEAD 变化
- 同一会话在绑定之后又结束了一轮，且核对发现上述任一项已变化；只聊天、没有改动工作树的轮次不影响绑定

聊天文本和 Agent 自述不参与合并成功判断。当前验收入口只投递合并指令，`prepareMerge` / `applyMerge` 是保留的旧 Git 实现，不在当前执行路径上。旧存档的 `pendingMergeCommit` 仍由恢复逻辑读取。

## 合并

1. 在任务锁内核对页面上的验收绑定、任务工作树干净、目标 HEAD 未变，确认原会话已空闲。协作任务还要向宿主确认当前主会话和会话验收状态。
2. 同一 Git 仓库不允许另一个任务同时合并。先保存 `mergeRequest`（独立消息 id、前一轮 turn id），再向原会话发送合并指令。
3. Agent 在任务工作树把最新目标分支合入任务分支，结合上下文解决冲突并验证，然后合入目标分支。指令要求保留双方历史，不覆盖用户的未提交改动，不推送，不自行清理任务资源。
4. 插件后台监控原会话的当前轮次和权限状态。发送失败也不自动重发；旧轮次的结束事件不能完成新合并。
5. Agent 空闲后，插件用 Git 验证：已验收提交仍在任务分支历史中、任务分支全部提交已在目标分支中、验收时的目标历史仍保留、两边工作树干净且无未完成 Git 操作。再次检查引用没有在验证期间变化。
6. 验证成功才记为 `merged`，保存合并后的任务分支顶端，再进行清理。失败保留会话、工作树和分支，用户可在原会话继续处理。

验收页面上的 diff 以目标 HEAD 与成果提交的 merge-base 为起点（`a...b`），目标分支在任务开始后新增的提交不会显示成被任务删除。

重启不会重发保存的合并消息；它重新检查原会话与 Git 状态。不确定成功时保持待核对或失败。对于旧版保存的 `pendingMergeCommit`，目标引用等于该提交时记为已合并；目标仍等于旧绑定时退回待验收，其他情况待核对，不自动执行旧合并。

## 连接

插件在首次使用时连接 daemon，失败后下一次调用会重连。连不上时所有会话操作都返回 `gateway-unavailable`，不会把查不到的会话当成已停止：验收拒绝合并，取消保持 `canceling`，重启恢复只记下错误、不改状态。

## 持久化

`PASEO_TODO_DATA_DIR` 或 `$PASEO_HOME/paseo-todo`（默认 `~/.paseo/paseo-todo`）。`state.json` 用 zod strict 校验，临时文件改名写盘。损坏的文件不覆盖。工作树在该目录的 `worktrees/` 下，合并后按下面「合并后清理」删除。

## 合并后清理

合并成功后依次执行，前一步成功才做下一步，结果记在任务的 `cleanup` 上：

1. 归档该任务所有会话（按 `paseo-todo-task` 标签），以及在任务工作树上打开的那个工作区。只归档目录等于任务工作树的工作区，不碰项目自己的工作区。
2. `git worktree remove`，不加 `--force`：有未提交或未跟踪的文件时 git 拒绝，文件保留。被忽略的文件随工作树删除。
3. 删除任务分支：只删 `paseo-todo/` 前缀的分支，且分支顶端必须等于验证合并时保存的任务分支顶端（旧存档回退到验收成果提交）、该提交已在目标分支里、没有任何工作树检出它；用 `update-ref -d <分支> <预期顶端>` 比较后删除。

任一步失败都不影响已合并的结果，任务保持 `merged`，页面显示失败的一步并可重试清理；已完成的步骤不会重做。插件不切换用户检出的分支。

## 协作

待办保存的是任务自己的协作快照：关闭为 `null`，开启为 `full`（完整流程）或 `execute_review`（执行＋审核）。快照包含角色、模型、权限、提示词和限制，字段与宿主协作设置一致。关闭协作的单 Agent 任务把思考强度存在 `thinkingOptionId`；空值表示供应商默认，创建会话时写入 `agent.create` 的 config。换模型会清掉上一次的选择。`execute_review` 必须有独立审核 Agent。任务工作树已经隔离，启动时 `conversation.open` 使用 `isolation=local`，不再开第二个工作树。

当前宿主会用全局角色提示词覆盖 `conversation.open` 中的 `settings.rolePrompts`。表单和启动前检查都要求显式填写的任务提示词与主机一致；留空表示使用主机默认。不同则报错，不投递目标，也不通过修改全局提示词来绕过限制。当前两角色表单由审核 Agent 担任主会话，执行 Agent 使用独立会话；可选的先规划也由审核角色负责。旧任务仍保留各自保存的角色快照。多个角色可以共享一个配置，单独修改其中一个角色时会拆出独立配置，避免丢失选择或修改另一个角色。

工具栏没有单独的协作入口。协作只在新建任务的同一个对话框里设置，不调用宿主的 `settings.save` 或 `prompts.save`，也不改宿主全局角色提示词。从未保存和明确关闭都会让新任务默认关闭；宿主目录只用来预填表单。加入待办时把当时的快照写到任务上，并在这个浏览器记住该机器的选择（`localStorage`，`paseo-todo.collaboration-defaults.v1`），下次新建从这里开始。已经在列表里的任务不变。

草稿且还没有 operation id 时，卡片上的编辑操作打开任务编辑器；详情页也可直接编辑协作副本。取消不写盘。保存失败或校验失败时保留正在编辑的内容。有未保存的修改时，这个任务的「开始」以及它所在机器的「全部开始」都不会启动，避免队列把修改丢掉。已取消的任务同样可以改：它的运行已经结束，重试会用新设置新建会话，保留的工作树和分支继续使用。其他已开始的任务协作设置只读，并显示已保存的摘要和宿主阶段、控制状态、会话验收。换机器会重新读取那台机器的能力和默认值，不把另一台机器的模型带过去。

宿主不支持协作、不能按任务应用设置，或没有执行＋审核时，页面显示错误。开启协作的任务不会静默降成单个 Agent。启动顺序是先打开任务工作区，再用该任务的 operation id 调用 `conversation.open`，由宿主在启用协作之后投递目标。

取消、需要新会话的重试和继续修改都会先停止宿主上的协作 run，再处理主 Agent，并确认主 Agent 已停止。受阻 run 的重试保留原 operation id 和 run，先排队取得仓库执行名额，再调用宿主 retry。重启恢复按 operation id 找回会话，不重复投递目标；启动回包丢失时也用宿主的 requestId 绑定找回，而不是依赖普通 Agent 的标签。重试和继续修改沿用任务上的快照，启动前只读取宿主提示词以验证兼容性。

插件每两秒在后台同步协作状态，页面关闭不影响队列推进；退出前等待进行中的同步完成，再释放存储锁。协作仍在设计、执行、审核或等待方案时，待办保持执行中。等待会话验收时，主操作是打开会话，不是验收并合并。会话验收完成之后，待办仍用原来的成果绑定，要用户在这个页面上明确确认才合并。真正取得合并锁后还会复核会话已验收，避免异步检查期间验收状态改变。成果绑定失效后，同一已完成 run 的轮询不会重新固化后续本地改动；只有观测到宿主重新执行，或开启新一轮任务，才允许创建新绑定。

## 不做

依赖图、自动推送、以及阻止有 shell 权限的 Agent 自己执行 Git。插件自己的代码路径不会因为轮次结束、权限回调或聊天内容去合并或推送。

## 前端刷新

各主机独立轮询列表。操作完成后的强制刷新会替代之前的请求；旧请求的成功或错误均不覆盖新结果，旧请求结束也不会解除新请求的占用。切换项目作用域或卸载时使旧响应失效。
